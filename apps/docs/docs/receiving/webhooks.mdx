title: "Receive webhooks"
description: "Receive delivery status updates and inbound texts from any provider as verified SmsEvent objects, in Next.js, Hono, or Bun.serve."
---

Providers tell you whether a message arrived, and pass on texts people send to your number, by calling a URL on your server. `parseSmsWebhook()` checks that the request really came from the provider, then gives you the same `SmsEvent` shape for all six providers.

A successful `send()` only means the provider accepted the message. Whether it reached the phone arrives later, as a webhook.

## One handler

```ts sms-webhook.ts
import { parseSmsWebhook, WebhookSignatureError, type SmsEvent } from "@opencoredev/sms-sdk/webhooks";
import { db } from "./db";

export async function handleSmsWebhook(request: Request): Promise<Response> {
  let event: SmsEvent;
  try {
    event = await parseSmsWebhook({
      provider: "telnyx",
      request,
      credentials: { publicKey: process.env.TELNYX_PUBLIC_KEY ?? "" },
    });
  } catch (error) {
    if (error instanceof WebhookSignatureError) {
      return new Response("Invalid signature", { status: 401 });
    }
    throw error;
  }

  if (!(await db.webhookEvents.insertIfNew(event.dedupeKey))) {
    return new Response(null, { status: 200 }); // a repeat: acknowledge and stop
  }

  switch (event.type) {
    case "message.delivered":
    case "message.undelivered":
    case "message.filtered":
      await db.messages.updateStatus(event.providerId, event.type, event.errorCode);
      break;
    case "message.received":
      await db.inbox.save({ from: event.from, to: event.to, body: event.body, providerId: event.providerId });
      break;
    case "recipient.opted_out":
      await db.suppressions.add(event.from);
      break;
  }
  return new Response(null, { status: 200 });
}
```

The handler answers 401 to forged requests, acknowledges repeats without handling them twice, and records the events it cares about. For another provider, change `provider` and `credentials`; each provider's credentials are listed in [Webhook security](/receiving/webhook-security#how-each-provider-signs).

`parseSmsWebhook()` reads the raw body itself, because the signature covers the exact bytes. Do not read or parse the body before calling it.

:::warning[Twilio and Plivo sign the URL]
Behind a proxy or on most hosting platforms, your app sees a different URL from the one the provider called, and verification fails. Pass `publicUrl` with the exact URL from the provider console. See [Webhook security](/receiving/webhook-security#fix-url-mismatches-behind-a-proxy).
:::

### Next.js

```ts route.ts
import { handleSmsWebhook } from "./sms-webhook";

export const runtime = "nodejs";

export async function POST(request: Request): Promise<Response> {
  return handleSmsWebhook(request);
}
```

Put this in `app/api/webhooks/sms/telnyx/route.ts` and import the handler from your own module path. Next.js does not cache `POST` route handlers, so every request runs. Keep provider secrets in `.env.local` and your host's settings, and never prefix them with `NEXT_PUBLIC_`, which ships them to the browser. Sending from route handlers and server actions works the same way; with the `server-only` package installed, add `import "server-only";` to the module that creates `sms`.

### Hono

```ts
import { Hono } from "hono";
import { handleSmsWebhook } from "./sms-webhook";

const app = new Hono();

app.post("/webhooks/sms/telnyx", (c) => handleSmsWebhook(c.req.raw));

export default app;
```

Pass `c.req.raw`, the untouched web `Request`. Do not call `c.req.json()`, `c.req.text()`, or `c.req.parseBody()` first: the body can be read only once. The same app runs on Node.js with `@hono/node-server`.

### Bun.serve

```ts
import { handleSmsWebhook } from "./sms-webhook";

Bun.serve({
  port: 3000,
  fetch(request) {
    const { pathname } = new URL(request.url);
    if (request.method === "POST" && pathname === "/webhooks/sms/telnyx") {
      return handleSmsWebhook(request);
    }
    return new Response("Not found", { status: 404 });
  },
});
```

Bun loads `.env` automatically, so `TELNYX_PUBLIC_KEY` comes from your `.env` file in development.

SMS SDK is tested on Node.js and Bun. Edge runtimes have the APIs it needs but are not tested. On serverless platforms, store the event before you respond, because the platform can stop the function right after the response. `memoryIdempotencyStore()` does not survive across serverless invocations, so use a [shared store](/advanced/multiple-instances) there. To test locally, expose your port with a tunnel and use its HTTPS URL; see [Local testing](/getting-started/local-testing).

## Event types

| `type` | When |
| --- | --- |
| `message.queued`, `message.sent`, `message.delivered`, `message.undelivered`, `message.filtered` | The status of a message you sent changed. |
| `message.received` | Someone texted your number. |
| `recipient.opted_out`, `recipient.opted_in`, `recipient.help` | Someone replied STOP, START, or HELP. See [STOP, HELP, and opt-outs](/receiving/opt-outs). |
| `unrecognized` | A verified event SMS SDK does not map, such as Twilio `read`. `providerEventType` names it and `raw` holds the payload. |

Every event has `provider`, `dedupeKey`, and `raw`, plus `occurredAt` when the payload includes a time. A provider adding a status gives you `unrecognized` instead of breaking your handler. The full shapes are in [Webhook events](/reference/webhook-events).

## Delivery status

Tell the provider where to send status updates, either per message with `webhookUrl` or once in its console:

| Provider | Status URL |
| --- | --- |
| Twilio | `webhookUrl` (sent as `StatusCallback`), or the Messaging Service's status callback. |
| Telnyx | `webhookUrl`, or the messaging profile's webhook URL. |
| Plivo | `webhookUrl` (sent as `url` with `method: "POST"`). |
| Vonage | `webhookUrl`, or the Vonage application's Status URL. Needs JWT auth; with Basic auth Vonage sends no status webhooks. |
| Bandwidth | The callback URL on your messaging application. A per-message `webhookUrl` is rejected as unsupported. |
| Sinch | `webhookUrl` (sent as `callback_url`), or the service plan's callback URL. Set `providerOptions.sinch.deliveryReport`, such as `"per_recipient"`, to receive reports. |

```ts
import { db } from "./db";
import { sms } from "./sms";

const result = await sms.send({
  to: "+14155550123",
  body: "Your order has shipped.",
  webhookUrl: "https://example.com/webhooks/sms/telnyx",
});
await db.messages.create({ id: result.id, provider: result.provider, providerId: result.providerId, to: "+14155550123", status: result.delivery });
```

Save `result.providerId`. Status events carry the same ID in `event.providerId`, along with `providerStatus` (the provider's own word, such as `undelivered`) and `errorCode`, `from`, and `to` when the provider sent them.

### Status mapping

| Event | Twilio | Telnyx | Plivo | Vonage | Bandwidth | Sinch |
| --- | --- | --- | --- | --- | --- | --- |
| `message.queued` | queued, accepted, scheduled, sending | queued, sending | queued | (none) | message-sending | Queued, Pending |
| `message.sent` | sent | sent, delivery_unconfirmed | sent | submitted | (none) | Sent, Accepted |
| `message.delivered` | delivered | delivered | delivered | delivered | message-delivered | Delivered |
| `message.undelivered` | undelivered, failed | sending_failed, delivery_failed, expired | undelivered, failed | rejected, undeliverable | message-failed | Failed, Undelivered, Expired; Rejected or Filtered without code 40003 |
| `message.filtered` | a failure with error 30007 | a failure with error 40002, 40003, or 40322 | never | a failure with error 1210, 1470, 1472, or 1480 to 1483 | never | Rejected or Filtered with code 40003 |

`message.filtered` means a carrier or the provider blocked the message as spam or for its content. It needs one of the error codes above; any other failure stays `message.undelivered`. Telnyx status events come from its `message.sent` and `message.finalized` webhooks.

`delivered` means the carrier reported delivery to the handset, and not every carrier does. Some routes stop at `sent`, and Telnyx reports `delivery_unconfirmed` when there is no receipt. Treat `message.sent` with nothing after it as probably delivered. SMS SDK does not poll for status, so if a webhook never arrives, look the message up with the provider.

## Inbound messages

Texts to your number go to the URL set on the number or its group. A per-message `webhookUrl` only affects status events.

| Provider | Inbound URL |
| --- | --- |
| Twilio | The number's "A message comes in" webhook, or the Messaging Service's incoming message setting. |
| Telnyx | The messaging profile's inbound webhook URL. |
| Plivo | The message URL of the Plivo application linked to the number. |
| Vonage | The Inbound URL of the Vonage application linked to the number. Send from a linked number with JWT auth; Vonage rejects Basic auth for linked numbers with a 401. |
| Bandwidth | The callback URL on the messaging application. |
| Sinch | The service plan's callback URL. |

A `message.received` event has `providerId`, `from` (the sender), `to` (your number), `body`, and `mediaUrls`. Media comes from Twilio, Telnyx, Plivo, and Bandwidth; it is always empty for Vonage and Sinch. Media URLs point at provider storage, may expire, and may need provider credentials to fetch. Vonage and Sinch numbers that arrive without `+` are normalized to E.164.

A message that is only a keyword such as STOP or HELP arrives as a `recipient.*` event instead. See [STOP, HELP, and opt-outs](/receiving/opt-outs).

SMS SDK never replies on its own and does not store conversations. To answer, send from the number that was texted, and derive the idempotency key from the inbound event so a repeated webhook cannot send a second reply:

```ts
import { isE164 } from "@opencoredev/sms-sdk";
import type { SmsEvent } from "@opencoredev/sms-sdk/webhooks";
import { sms } from "./sms";

export async function reply(event: SmsEvent): Promise<void> {
  if (event.type !== "message.received" || !isE164(event.from) || !isE164(event.to)) return;
  await sms.send({
    to: event.from,
    from: event.to,
    body: "Thanks, we got your message.",
    idempotencyKey: `reply:${event.dedupeKey}`,
  });
}
```

This protects you only when the client has an [idempotency store](/sending/idempotency). Twilio also lets you reply by returning TwiML. SMS SDK does not build TwiML; to send no reply, return `<Response></Response>` with `Content-Type: text/xml`.

## Duplicates and ordering

Providers retry webhooks that fail or time out, and send events in parallel. The same event can arrive twice, and `message.sent` can arrive after `message.delivered`.

Deduplicate on `dedupeKey`, which stays the same each time the provider delivers an event:

| Provider | `dedupeKey` |
| --- | --- |
| Twilio | `twilio:{MessageSid}:{MessageStatus}` or `twilio:{MessageSid}:received` |
| Telnyx | `telnyx:{data.id}`, the webhook event ID |
| Plivo | `plivo:{MessageUUID}:{Status}` or `plivo:{MessageUUID}:received` |
| Vonage | `vonage:{message_uuid}:{status}` or `vonage:{message_uuid}:received` |
| Bandwidth | `bandwidth:{message.id}:{type}` |
| Sinch | `sinch:{batch_id}:{recipient}:{status}` or `sinch:{id}:received` |

`insertIfNew` must be atomic, such as `INSERT ... ON CONFLICT DO NOTHING` that returns whether a row was inserted. Reading first and inserting second lets two parallel deliveries both pass. Keep keys at least as long as the provider retries, typically a day or more. Answer repeats with a 2xx, because an error makes the provider retry again. Respond fast and do slow work in a background job, since a timeout also causes a retry.

Never let a late event move a message backward. Rank the statuses and keep the highest:

```ts
import type { MessageStatusType } from "@opencoredev/sms-sdk/webhooks";

const rank: Record<MessageStatusType, number> = {
  "message.queued": 0,
  "message.sent": 1,
  "message.delivered": 2,
  "message.undelivered": 2,
  "message.filtered": 2,
};

export function nextStatus(current: MessageStatusType | undefined, incoming: MessageStatusType): MessageStatusType {
  if (current === undefined) return incoming;
  return rank[incoming] >= rank[current] ? incoming : current;
}

console.log(nextStatus("message.delivered", "message.sent")); // "message.delivered"
```

The final states share a rank, so the last one to arrive wins. Providers rarely send two different final states; when they do, `occurredAt`, if present, says which came later.

A status webhook can also arrive before you have saved the `send()` result. Upsert the status row by `providerId`, or hold unknown IDs briefly and apply them once the send result is saved.
